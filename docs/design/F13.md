# F13 — Planner v2: Categories, Day & Week Views, Recurring Blocks

Spec: M2 items 1, 6, 7. Flag: `FEATURE_F13`. Base: `main` in `discipline`, `discipline-back`, `discipline-py`.
Out of scope: commitments & ICS (M2 #2, #4), weekly targets (M2 #3), Smart Schedule redesign (M2 #9/M6), tasks & Top-3 (M2 #8/F10).

Revision 2 (2026-11-19) — review fixes: a deterministic backfill that keeps every category, a
nullable `category_id` with lazy defaults during the deploy, bounded materialization, exceptions
instead of `skipped`, `NO ACTION` foreign keys, and no client-side materialization.

## 1. Stories and acceptance criteria

- **S1: Categories (api, web, analytics).**
  - Table `categories`: `user_id`, `name`, `color`, `icon`, `kind` (`focus`, `study`, `admin`,
    `exercise`, `rest`, `personal`), `system_key`, `name_custom`.
  - AC: six defaults per user (`deep_work`/focus, `study`/study, `admin`/admin,
    `exercise`/exercise, `rest`/rest, `personal`/personal). They are created **lazily**, the
    first time a user's categories are read or written, so a sign-up during the deploy also gets
    them (§2.3). A default stores its `system_key` and no name of its own: the web shows the
    translated name (uz/ru/en) until the user renames it, which sets `name_custom = true`.
  - AC: migration 00014 gives **every** existing block a category: one category per distinct
    legacy `tasks.category` string per user, mapped to a kind where we know it, `personal`
    otherwise. No block loses its category and no custom string is collapsed into Personal
    (M2 acceptance).
  - AC: `GET /categories`, `POST /categories`, `PUT /categories/:id`,
    `DELETE /categories/:id[?reassignTo=<id>]`. Without `reassignTo`, a category still in use
    answers 409 `category_in_use`.
  - AC: names are unique per user, case-insensitively: `UNIQUE (user_id, lower(name))`.
  - AC: analytics (`day_metrics`) aggregate by category `kind`, never by name.

- **S2: Day and Week planner views (web).**
  - AC: Day view: 00:00–24:00 vertical timeline, 15-minute grid, auto-scrolls to now.
  - AC: Week view: 7 columns (Mon–Sun) from 768 px; on a phone one day column with a weekday
    pill header (no 3-day view — §10.1).
  - AC: drag/resize in 15-minute steps with a mouse; on touch a long press (≥ 400 ms) picks a
    block up, a normal swipe still scrolls.
  - AC: a form dialog does everything the gestures do, for keyboard and screen-reader users;
    changes are announced with `aria-live="polite"`.
  - AC: both views have empty, loading, error and offline states (§5.4).

- **S3: Recurring blocks (api, web).**
  - AC: a rule has weekdays (ISO 1–7, non-empty), start/end minutes, `valid_from`, optional
    `valid_to`, and a category.
  - AC: occurrences are materialized server-side when a range is requested, bounded to at most
    42 days per request, never before today, never more than 8 weeks ahead (§4.1).
  - AC: "this one" edits only that occurrence and marks it as edited by hand.
  - AC: "this and following" splits the rule and **keeps** the occurrences the user had already
    edited individually (§4.4).
  - AC: deleting one occurrence, and a conflict with an existing block, write a
    `recurring_exceptions` row — never `status = 'skipped'`, which counts against the user (§4.3).

- **S4: Overlap rule with skipped and moved blocks (api).**
  - AC: `checkOverlap` keeps ignoring blocks with `status IN ('skipped', 'moved')` (F1 behaviour).
  - AC: materialization never touches an existing block: a clash creates no occurrence and
    records a `conflict` exception instead.

- **S5: E2E phone planning test (web).**
  - AC: Playwright at 390×844: a university timetable, gym 3×/week and 4 focus blocks are
    planned in one scripted pass, with no console error and no horizontal scroll.

### 2.1 Migration 00014 (expand)

-- +goose Up
CREATE TABLE categories (

    user_id     bigint      NOT NULL REFERENCES users (id) ON DELETE CASCADE,

    legacy_name varchar(64),

    CONSTRAINT chk_categories_icon  CHECK (icon IN (

);
CREATE UNIQUE INDEX uq_categories_user_name   ON categories (user_id, lower(name));
CREATE UNIQUE INDEX uq_categories_user_system ON categories (user_id, system_key) WHERE system_key IS NOT NULL;
CREATE UNIQUE INDEX uq_categories_user_legacy ON categories (user_id, legacy_name) WHERE legacy_name IS NOT NULL;

CREATE TABLE recurring_rules (
    id          bigserial PRIMARY KEY,
    user_id     bigint       NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    -- NO ACTION (the default): a DELETE that removes the user's categories and rules in the
    -- same statement still works, while a category that is in use cannot be deleted on its own.
    category_id bigint       NOT NULL REFERENCES categories (id),

    end_min     integer      NOT NULL,

    CONSTRAINT chk_recurring_dates    CHECK (valid_to IS NULL OR valid_to >= valid_from),

        AND array_length(weekdays, 1) BETWEEN 1 AND 7
        AND array_position(weekdays, NULL) IS NULL

);
CREATE INDEX idx_recurring_rules_user_dates ON recurring_rules (user_id, valid_from, valid_to);

-- A date a rule deliberately has no block on. Never a block with status 'skipped': skipped
-- counts against the user, and these are not misses (VISION: rest is never shown as failure).
CREATE TABLE recurring_exceptions (
    id         bigserial PRIMARY KEY,
    user_id    bigint      NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    rule_id    bigint      NOT NULL REFERENCES recurring_rules (id) ON DELETE CASCADE,
    date       date        NOT NULL,
    reason     varchar(16) NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),

ALTER TABLE tasks ADD CONSTRAINT chk_tasks_source

### 2.2 Backfill: one category per legacy string, nothing collapsed

The mapping is computed **once**, so both statements agree and the result cannot depend on row
order (goose runs the migration in a transaction, so the temp table is gone afterwards):

```sql
-- +goose StatementBegin
CREATE TEMP TABLE legacy_map ON COMMIT DROP AS
SELECT DISTINCT
    t.user_id,
    lower(btrim(t.category)) AS legacy,
    CASE lower(btrim(t.category))
        WHEN 'deep-work' THEN 'Deep Work' WHEN 'deep work' THEN 'Deep Work'
        WHEN 'study'     THEN 'Study'     WHEN 'admin'     THEN 'Admin'
        WHEN 'gym'       THEN 'Gym'       WHEN 'exercise'  THEN 'Gym'
        WHEN 'rest'      THEN 'Rest'      WHEN 'fixed'     THEN 'Fixed'
        ELSE left(btrim(t.category), 64)
    END AS name,
    CASE lower(btrim(t.category))
        WHEN 'deep-work' THEN 'focus'    WHEN 'deep work' THEN 'focus'
        WHEN 'study'     THEN 'study'    WHEN 'admin'     THEN 'admin'
        WHEN 'gym'       THEN 'exercise' WHEN 'exercise'  THEN 'exercise'
        WHEN 'rest'      THEN 'rest'
        ELSE 'personal'                      -- 'fixed' and anything custom
    END AS kind,
    CASE lower(btrim(t.category))
        WHEN 'deep-work' THEN 'deep_work' WHEN 'deep work' THEN 'deep_work'
        WHEN 'study'     THEN 'study'     WHEN 'admin'     THEN 'admin'
        WHEN 'gym'       THEN 'exercise'  WHEN 'exercise'  THEN 'exercise'
        WHEN 'rest'      THEN 'rest'
        ELSE NULL                            -- a user-made category has no system key
    END AS system_key
FROM tasks t
WHERE t.category IS NOT NULL AND btrim(t.category) <> '';
-- +goose StatementEnd

-- One category per (user, mapped name), case-insensitively, so two legacy strings that map to
-- the same name ('gym'/'exercise', 'deep-work'/'deep work', 'Reading'/'reading') share one
-- category and uq_categories_user_name cannot be violated. DISTINCT ON + ORDER BY makes the
-- survivor deterministic and prefers the mapped row (the one with a system key).
INSERT INTO categories (user_id, name, color, icon, kind, system_key, legacy_name)
SELECT DISTINCT ON (m.user_id, lower(m.name))
       m.user_id, m.name, d.color, d.icon, m.kind, m.system_key, m.legacy
  FROM legacy_map m
  JOIN (VALUES
      ('focus',    '#3B82F6', 'target'),
      ('study',    '#8B5CF6', 'book-open'),
      ('admin',    '#6B7280', 'briefcase'),
      ('exercise', '#10B981', 'dumbbell'),
      ('rest',     '#F59E0B', 'coffee'),
      ('personal', '#EC4899', 'user')
  ) AS d(kind, color, icon) ON d.kind = m.kind
 ORDER BY m.user_id, lower(m.name), (m.system_key IS NULL), m.legacy;

-- Deterministic: exactly one category matches a (user, legacy string) pair.
UPDATE tasks t
   SET category_id = c.id
  FROM legacy_map m
  JOIN categories c ON c.user_id = m.user_id AND lower(c.name) = lower(m.name)
 WHERE m.user_id = t.user_id AND m.legacy = lower(btrim(t.category));

CREATE INDEX idx_tasks_category_id ON tasks (category_id);
CREATE UNIQUE INDEX uq_tasks_recurring_slot ON tasks (user_id, recurring_rule_id, date)
    WHERE recurring_rule_id IS NOT NULL;
```

Known legacy strings (from the F1 code and the smart schedule): `deep-work`, `study`, `admin`,
`gym`, `rest`, `fixed`. `fixed` is a commitment, not exercise or focus, so it keeps its own
category of kind `personal` with the translated name it already has (`categories.fixed`).
A block whose category string is empty keeps `category_id = NULL` and gets the user's Personal
category when the API next touches it; 00015 refuses to run while any `NULL` is left.

### 2.3 The trigger, and lazy defaults

While the previous API version is still running it inserts blocks with the legacy string and no
`category_id`. The trigger fills the id and **never writes `tasks.category`** — overwriting the
legacy string would rename a custom category under the old client and break a rollback:

```sql
-- +goose StatementBegin
CREATE FUNCTION tasks_fill_category_id() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE
    want_name text;
    want_kind text;
    want_key  text;
BEGIN
    IF NEW.category_id IS NOT NULL OR NEW.category IS NULL OR btrim(NEW.category) = '' THEN
        RETURN NEW;                       -- the new API sends the id; nothing to do
    END IF;
    SELECT CASE lower(btrim(NEW.category))
               WHEN 'deep-work' THEN 'Deep Work' WHEN 'deep work' THEN 'Deep Work'
               WHEN 'study' THEN 'Study' WHEN 'admin' THEN 'Admin'
               WHEN 'gym' THEN 'Gym' WHEN 'exercise' THEN 'Gym'
               WHEN 'rest' THEN 'Rest' WHEN 'fixed' THEN 'Fixed'
               ELSE left(btrim(NEW.category), 64) END,
           CASE lower(btrim(NEW.category))
               WHEN 'deep-work' THEN 'focus' WHEN 'deep work' THEN 'focus'
               WHEN 'study' THEN 'study' WHEN 'admin' THEN 'admin'
               WHEN 'gym' THEN 'exercise' WHEN 'exercise' THEN 'exercise'
               WHEN 'rest' THEN 'rest' ELSE 'personal' END,
           CASE lower(btrim(NEW.category))
               WHEN 'deep-work' THEN 'deep_work' WHEN 'deep work' THEN 'deep_work'
               WHEN 'study' THEN 'study' WHEN 'admin' THEN 'admin'
               WHEN 'gym' THEN 'exercise' WHEN 'exercise' THEN 'exercise'
               WHEN 'rest' THEN 'rest' ELSE NULL END
      INTO want_name, want_kind, want_key;

    -- A user who signed up during the deploy has no categories yet: make this one now.
    INSERT INTO categories (user_id, name, color, icon, kind, system_key)
    VALUES (NEW.user_id, want_name,
            CASE want_kind WHEN 'focus' THEN '#3B82F6' WHEN 'study' THEN '#8B5CF6'
                           WHEN 'admin' THEN '#6B7280' WHEN 'exercise' THEN '#10B981'
                           WHEN 'rest' THEN '#F59E0B' ELSE '#EC4899' END,
            CASE want_kind WHEN 'focus' THEN 'target' WHEN 'study' THEN 'book-open'
                           WHEN 'admin' THEN 'briefcase' WHEN 'exercise' THEN 'dumbbell'
                           WHEN 'rest' THEN 'coffee' ELSE 'user' END,
            want_kind, want_key)
    ON CONFLICT DO NOTHING;

    SELECT id INTO NEW.category_id FROM categories
     WHERE user_id = NEW.user_id AND lower(name) = lower(want_name);
    RETURN NEW;
END;
$$;
-- +goose StatementEnd
CREATE TRIGGER trg_tasks_fill_category_id BEFORE INSERT OR UPDATE OF category ON tasks
    FOR EACH ROW EXECUTE FUNCTION tasks_fill_category_id();
```

The new API creates the six defaults lazily, in one `INSERT … ON CONFLICT (user_id, system_key)
DO NOTHING` per user, the first time it reads or writes that user's categories
(`EnsureDefaultCategories(userID)`), so sign-up needs no change and a user created by the old
version is complete the moment the new version serves them.

Down migration: drop the trigger and function, the three new indexes, the four `tasks` columns,
restore `chk_tasks_source` to `('manual', 'smart-schedule')` (after
`UPDATE tasks SET source = 'manual' WHERE source = 'recurring'`), then drop
`recurring_exceptions`, `recurring_rules`, `categories`. `tasks.category` is untouched
throughout, so the old code works again immediately.

## 3. API & contracts

### 3.1 Endpoints (all behind `FEATURE_F13`)

- `GET /categories` → `{ categories: Category[] }` (creates the defaults if the user has none).
- `POST /categories` `{ name, color, icon, kind }` → 201 `{ category }`.
- `PUT /categories/:id` `{ name?, color?, icon? }` → 200. `kind` is immutable; a new `name` sets
  `nameCustom = true`.
- `DELETE /categories/:id[?reassignTo=<id>]` → 204. With `reassignTo`, every block and rule moves
  to that category in one transaction (same user, different id, else 400 `category_invalid`).
  Without it, a category in use answers 409 `category_in_use`. A default can be deleted once it
  is empty; it comes back as a default only if the user has none left.
- `GET /recurring-rules` → `{ rules: RecurringRule[] }` (active and future).
- `POST /recurring-rules` `{ categoryId, name, weekdays, startMin, endMin, validFrom, validTo? }`
  → 201. `weekdays` are ISO numbers, sorted and de-duplicated by the API before the insert.
- `PUT /recurring-rules/:id?scope=all|following&fromDate=YYYY-MM-DD` → 200 `{ rules: [...] }`
  (`following` answers with both halves of the split).
- `DELETE /recurring-rules/:id?scope=all|following&fromDate=YYYY-MM-DD` → 204.
- `DELETE /tasks/:id/occurrence` → 204. Deletes one occurrence of a rule and records a
  `cancelled` exception (§4.3). `DELETE /tasks/:id` keeps its F1 meaning for a plain block.
- `POST /recurring-rules/:id/occurrences/:date/place-anyway` → 201 `{ task }`. Creates the
  occurrence the conflict skipped, overlapping on purpose (§10.2).
- `GET /tasks?startDate=&endDate=` materializes the range first (§4.1) and returns
  `{ tasks, exceptions, truncated }`. The existing `GET /tasks?date=` is unchanged.
- `POST /tasks/:id/move` keeps its F1 semantics; moving an occurrence sets `original_date`,
  `recurring_edited = true` and writes a `moved` exception for the original date.

Errors: `category_not_found`, `category_in_use`, `category_name_taken`, `category_invalid`,
`category_kind_invalid`, `category_color_invalid`, `category_icon_invalid`,
`recurring_rule_not_found`, `recurring_dates_invalid`, `recurring_weekdays_invalid`,
`range_too_long`, `occurrence_not_found`.

### 3.2 Contracts (`discipline/contracts/`, generated from zod — never hand-edited)

- `categories.schema.json`: `Category` = `{ id, name, color, icon, kind, systemKey: string|null,
  nameCustom: boolean }`. `color` is `^#[0-9A-F]{6}$`; `icon` and `kind` are enums matching the
  CHECKs in §2.1. The web renders `nameCustom ? name : t('categories.' + systemKey)`.
- `blocks.schema.json`: `Block` gains `categoryId: number|null`, `categoryKind` (enum),
  `recurringRuleId: number|null`, `originalDate: string|null`, `recurringEdited: boolean`.
  `category` (the legacy string) stays in the schema until the column goes.
- `recurring.schema.json`: `RecurringRule`, `RecurringException`
  (`{ ruleId, date, reason: 'cancelled'|'conflict'|'moved' }`), and the `GET /tasks` range
  response `{ tasks, exceptions, truncated: boolean }`.
- `events.schema.json`: adds `week_planned` (§7).
- After changing a zod schema: `npm run contract:update` and commit `contracts/`.

## 4. Recurring blocks: materialization, exceptions, splits

### 4.1 Materialization (server-side only), with limits

`GET /tasks?startDate=&endDate=` runs, in one transaction per user:

1. Reject a range longer than **42 days** with 400 `range_too_long` (the week view asks for 7,
   the month overview for 42).
2. Clamp the range before materializing: `from = max(startDate, today)` and
   `to = min(endDate, today + 56 days)`. **Dates before today are never materialized** — a block
   created in the past would count as missed the moment it appears — and nothing is created more
   than **8 weeks** ahead, so a rule cannot fill the table. When the clamp cut something off, the
   response says `truncated: true` and the week view shows "planned up to <date>".
3. Read the rules overlapping `[from, to]`: `valid_from <= to AND (valid_to IS NULL OR valid_to >= from)`.
4. For each rule and each matching weekday date in `[from, to]` (weekday computed in the user's
   time zone): skip the date when a `recurring_exceptions` row exists for `(rule, date)`, or a
   `tasks` row already exists for `(user, rule, date)` or with `original_date = date`.
5. Otherwise insert `source = 'recurring'`, `status = 'planned'`, the rule's category and
   minutes, `INSERT … ON CONFLICT DO NOTHING` against `uq_tasks_recurring_slot` so two devices
   racing create one row.
6. A clash with an existing active block (the F1 overlap check, which ignores `skipped` and
   `moved`) creates **no** block: it writes a `conflict` exception instead (§10.2).
7. Dates in the past are returned from storage as they are: a user looking at last week sees what
   actually happened, not newly invented blocks.

Reads are idempotent, so a `GET` repeated by two devices converges on the same rows.

### 4.2 Weekdays and `time.Weekday`

Rules store ISO weekdays: Monday = 1 … Sunday = 7. Go's `time.Weekday` is Sunday = 0 …
Saturday = 6, so the API converts with `iso := (int(t.Weekday())+6)%7 + 1` (and back with
`time.Weekday(iso % 7)`). Both directions are unit-tested across a Sunday, because `Sunday = 0`
is the easy mistake. Postgres' `extract(isodow from date)` already returns 1–7 and is what the
materialization SQL uses.

### 4.3 Exceptions instead of `skipped`

| What the user does | What is stored |
|---|---|
| "Delete just this one" | the occurrence row is deleted (it is untouched) or kept if already done; a `cancelled` exception for `(rule, date)` |
| Materialization hits a clash | no block; a `conflict` exception |
| Moves an occurrence to another day | the row keeps `recurring_rule_id`, gets `original_date` and `recurring_edited = true`; a `moved` exception for the original date |

Exceptions are not blocks: they never appear in `day_metrics`, in planned or done minutes, in a
streak, or anywhere a miss is counted. `discipline-py` reads `tasks` only, so this holds by
construction; the analytics test asserts a day with an exception and no block counts as a day
with nothing planned, not as a missed block. The week view marks the date quietly ("not this
week"), never red, never "failed" (VISION: copy encourages, rest is never failure).

A block that was already `done` or `partial` is never deleted by a cancel: the history stays, the
exception stops the rule from re-creating it.

### 4.4 "This one" and "this and following"

- **This one:** `PUT /tasks/:id` or `POST /tasks/:id/move` on the occurrence. The row keeps
  `recurring_rule_id` and gets `recurring_edited = true`.
- **This and following** (`scope=following&fromDate=D`), in one transaction:
  1. the old rule gets `valid_to = D - 1` day;
  2. a new rule is inserted with `valid_from = D`, the edited values and `split_from_rule_id`;
  3. untouched future occurrences (`date >= D AND status = 'planned' AND NOT recurring_edited`)
     are deleted, so the new rule materializes them;
  4. occurrences the user **had edited individually** (`recurring_edited`) and occurrences that
     are already `done`, `partial`, `in_progress` or `moved` are **kept**, and their
     `recurring_rule_id` is re-pointed at the new rule so materialization sees them as present
     and does not duplicate them;
  5. exceptions on `date >= D` are re-pointed at the new rule as well, so a cancelled Wednesday
     stays cancelled across the split.
- **"This and following" delete:** step 1 and step 3 only; kept rows stay as plain history.
- **Scope `all`:** the rule is edited in place and only untouched future occurrences are
  re-materialized; the past is never rewritten.

## 5. Views, gestures and states (web)

### 5.1 Layout

- Desktop (≥ 768 px): 7 columns, 00:00–24:00 gutter, 15-minute grid, mouse drag and resize.
- Phone (390 px): one day column, a sticky weekday pill header (Mon–Sun, dots for how full a day
  is), horizontal swipe between days, auto-scroll to now. No 3-day view (§10.1).
- Touch targets ≥ 44 px, including the weekday pills and the resize handles.

### 5.2 Gestures

- `touch-action: pan-y` by default, so a swipe scrolls.
- Long press ≥ 400 ms picks a block up (`navigator.vibrate(20)` where supported, guarded); the
  block gets a shadow and `scale(1.02)`, handles appear, `touch-action: none` while dragging.
- Movement snaps to 15 minutes; release saves optimistically through `POST /tasks/:id/move` or
  `PUT /tasks/:id`; dragging off-screen or pressing Escape cancels without a save.

### 5.3 Form alternative (keyboard, screen reader)

"Edit" or double tap opens `BlockFormModal`: date, start/end selects in 15-minute steps,
category, and the recurring options ("only this one" / "this and following"). Labelled inputs,
focus trap, and every change announced through `aria-live="polite"`. Everything a gesture can do
is reachable here; the E2E keyboard pass does the whole flow without a pointer.

### 5.4 Empty, loading, error, offline — both views

| State | Day view | Week view |
|---|---|---|
| Empty | "Nothing planned yet" + "Add a block" (and "Add a repeating block" when the user has no rules) | the same, under the weekday pills, for the visible day |
| Loading | skeleton grid with the time gutter already drawn, so nothing jumps (`aria-busy`) | skeleton columns; the pill header renders at once |
| Error | the server's translated message + "Try again" (`errorMessage(err, 'planner.loadFailed')`), the grid stays readable | the same, per range request |
| Offline | the **last fetched week from the cache**, read-only for moves, with a banner "Offline — showing the week you last loaded"; edits are queued | the same banner above the pills; `truncated`/conflict markers are kept from the cached response |

Offline rules (B7): the client **never materializes** occurrences. A recurring rule created or
edited offline goes into the existing `sync-queue` (replay-safe, as in F1) and its occurrences
appear after the server answers; the view says "Repeating blocks appear once you are back
online". Block edits (move, resize, check-in) queue exactly as they do today, so no new offline
machinery is added.

## 7. Product events

Names live only in `discipline/contracts/events.ts` and are written by the API into
`product_events`. Already defined and reused as they are: `block_created`, `block_moved`,
`block_status_changed`. New: **`week_planned`**.

| Event | When | Props (no personal data) |
|---|---|---|
| `block_created` | a block is created, including a materialized occurrence | `source` (`manual`/`smart-schedule`/`recurring`), `category_kind` |
| `block_moved` | an occurrence or a block moves | `recurring` (bool), `same_day` (bool) |
| `block_status_changed` | F1 transitions, unchanged | `from`, `to` |
| `week_planned` | a week range is materialized and at least one occurrence or block was created | `created`, `conflicts`, `days` |

No event carries a category name, a rule name or a note: those are personal data (§8).
Recording follows F1 — only on a real transition, never on a replay — and the Go test keeps
asserting that the API writes no name the contract does not list.

## 8. Edge cases, security and privacy

- **Timezone & DST:** rules store wall-clock minutes, so 09:00 stays 09:00 after a clock change;
  weekday and "today" come from the user's IANA zone. Tests cover a spring-forward and a
  fall-back week, and a rule whose occurrence lands on the skipped hour (it keeps its minutes).
- **Midnight:** `end_min` up to 1440; a block crossing midnight is rejected in F13 (overnight
  commitments are F9a).
- **New user:** no rules, no blocks, six lazily created categories; both views show their empty
  state, never an error.
- **Several devices:** materialization is idempotent and guarded by `uq_tasks_recurring_slot`;
  the last write wins for a move, exactly as in F1.
- **Deleting a category:** 409 `category_in_use`, or `?reassignTo=<id>` in one transaction. The
  database uses `NO ACTION` (not `RESTRICT`), so deleting a **user** still works: the cascades
  remove that user's blocks, rules and categories in the same statement.
- **A rule whose category is deleted:** impossible — the rule is a use, so it blocks the delete
  or is reassigned.
- **Authorization:** every endpoint takes the user id from the verified token and every query
  filters by it; `reassignTo` and `:id` are both checked to belong to that user.
- **Export & delete:** `categories`, `recurring_rules` and `recurring_exceptions` join the user
  data export and the account deletion.
- **Logging:** category names, rule names and notes are personal data — never logged, never in
  Sentry context, never in an event prop.

## 10. Owner answers (decided 2026-11-19)

1. **No 3-day view for now.** The phone keeps one day column plus the weekday pills; a condensed
   3-day option is reconsidered only if the pills prove not to be enough.
2. **A conflicting occurrence is not created and never counted.** Materialization writes a
   `conflict` exception; the week view shows a quiet conflict marker on that slot with two
   actions: **"place anyway"** (`POST /recurring-rules/:id/occurrences/:date/place-anyway`,
   creating the overlapping block on purpose) and **"skip this week"** (turns the exception into
   `cancelled`, so the marker goes away). Truncating the duration automatically was rejected: a
   silently shortened block is worse than an honest clash.
3. **Yes to reassignment on delete:** `DELETE /categories/:id?reassignTo=<id>` moves every block
   and rule in one transaction; without the parameter a category in use still answers 409.

### Remaining questions

1. How long should exceptions be kept? They are tiny, but a daily rule cancelled for years grows
   without limit; a cleanup of `cancelled` exceptions older than, say, a year needs the worker
   that arrives in M4.
2. Should `GET /tasks?startDate=&endDate=` materialize at all, or should the week view call an
   explicit `POST /recurring-rules/materialize`? A GET with a side effect is unusual, but an
   extra round trip on every week change is worse; it stays a GET unless the owner objects.
3. May a rule's category be changed for the future only (a split), or does changing the category
   always apply to the whole rule? The current design treats it like any other field, so
   `scope=following` splits.

## 11. Rollout

- **Flag:** `FEATURE_F13` (API env var → `GET /api/features`; the web hides the views while it is
  off). Materialization only runs for a user when the flag is on.
- **Expand → migrate → switch → contract.** Every step must work with the previous schema and the
  previous version of the other services.
  1. `discipline-back`: deploy with migration 00014 (pre-deploy step), flag **off**.
     `category_id` is nullable and the trigger covers the still-running previous version.
  2. Wait for the api's deploy to be healthy, then `discipline-py` (reads `kind`, tolerates
     `category_id IS NULL` by falling back to the legacy string).
  3. Then `discipline` (web), flag still off.
  4. `FEATURE_F13=true` on staging, walk through the E2E flow, then production.
  5. The release after: migration 00015 (`SET NOT NULL`, drop the trigger).
- **Rollback:** before 00015, `goose down` on 00014 restores the previous schema and
  `tasks.category` has never been rewritten, so the previous API version runs unchanged.
