# F13 — Planner v2: Categories, Day & Week Views, Recurring Blocks

Spec: M2 items 1, 6, 7. Flag: `FEATURE_F13`. Base: `feat/F1` in `discipline`, `discipline-back`, `discipline-py`.
Out of scope: commitments & ICS (M2 #2, #4), weekly targets (M2 #3), Smart Schedule redesign (M2 #9/M6), tasks & Top-3 (M2 #8/F10).

## 1. Stories and acceptance criteria

- **S1: Categories with fixed kind (api, web, analytics).**
  - Table `categories`: user_id, name, color, icon, kind (`focus`, `study`, `admin`, `exercise`, `rest`, `personal`).
  - AC: Seeded at signup with 6 defaults (Deep Work/focus, Study/study, Admin/admin, Exercise/exercise, Rest/rest, Personal/personal).
  - AC: Migration 00014 maps existing `tasks.category` strings to `category_id`; triggers keep string column valid during deploy.
  - AC: Endpoints `GET /categories`, `POST /categories`, `PUT /categories/:id`, `DELETE /categories/:id` (cannot delete if referenced).
  - AC: Analytics metrics (`day_metrics`) evaluate by category `kind`, not category name strings.

- **S2: Day and Week Planner Views (web).**
  - AC: Day view: 00:00–24:00 vertical timeline, auto-scrolls to current time, 15-minute grid.
  - AC: Week view: 7 columns (Mon–Sun) on desktop (≥768 px); on mobile (390 px) displays 1 active day column with a swipeable 7-day pill header.
  - AC: Drag/resize in 15-minute steps on desktop.
  - AC: Touch: long-press (≥400 ms with haptic feedback) engages drag/resize; normal swipe scrolls smoothly without triggering moves.
  - AC: Accessible form alternative modal for keyboard and screen-reader users; announces changes via `aria-live`.

- **S3: Recurring Blocks (api, web).**
  - AC: Recurring rules: chosen weekdays (1–7), start/end minutes, valid_from, optional valid_to.
  - AC: Materialization: occurrences materialized per week on view/plan with unique constraint `(user_id, recurring_rule_id, date)`.
  - AC: Edit "this one": updates only that day's `tasks` row (sets `original_date` if date shifted).
  - AC: Edit "this and following": truncates old rule (`valid_to = date - 1`) and creates new rule starting at `date`.
  - AC: Delete "this one" marks block `skipped`; delete "this and following" truncates rule `valid_to`.

- **S4: Overlap rule with skipped and moved blocks (api).**
  - AC: `checkOverlap` ignores blocks with `status IN ('skipped', 'moved')`.
  - AC: Materializing recurring blocks never overwrites manual active blocks; conflicts materialize as `skipped` with note.

- **S5: E2E phone planning test (web).**
  - AC: Scripted Playwright E2E at 390×844 px verifies university timetable + 3×/wk gym + 4 focus blocks planned under 5 min.

    id          bigserial PRIMARY KEY,
    user_id     bigint NOT NULL REFERENCES users (id) ON DELETE CASCADE,
    category_id bigint NOT NULL REFERENCES categories (id) ON DELETE RESTRICT,
    name        varchar(120) NOT NULL,

    start_min   integer NOT NULL,

-- Alter tasks to link categories and recurring rules
ALTER TABLE tasks

    ADD COLUMN recurring_rule_id bigint REFERENCES recurring_rules (id) ON DELETE SET NULL,
    ADD COLUMN original_date     date;

-- Backfill category_id by matching legacy category strings
UPDATE tasks t SET category_id = c.id
FROM categories c
WHERE c.user_id = t.user_id AND (
    (LOWER(t.category) IN ('deep-work', 'deep work') AND c.kind = 'focus') OR
    (LOWER(t.category) = 'study' AND c.kind = 'study') OR
    (LOWER(t.category) = 'admin' AND c.kind = 'admin') OR

-- Trigger keeps legacy category string in sync during zero-downtime deploy
CREATE OR REPLACE FUNCTION tasks_sync_category_name() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    SELECT name INTO NEW.category FROM categories WHERE id = NEW.category_id;
    RETURN NEW;
END;
$$;
CREATE TRIGGER trg_tasks_category_name BEFORE INSERT OR UPDATE OF category_id ON tasks
FOR EACH ROW EXECUTE FUNCTION tasks_sync_category_name();

## 3. API & Contracts

### Endpoints
- `GET /categories`: returns list of user categories `{ categories: Category[] }`.
- `POST /categories`: `{ name, color, icon, kind }` -> 201 Created `{ category: Category }`.
- `PUT /categories/:id`: `{ name, color, icon }` -> 200 OK. (`kind` is immutable).
- `DELETE /categories/:id`: 204 No Content. 409 `category_in_use` if referenced by any block/rule.
- `GET /recurring-rules`: returns active recurring rules `{ rules: RecurringRule[] }`.
- `POST /recurring-rules`: `{ categoryId, name, weekdays, startMin, endMin, validFrom, validTo? }` -> 201.
- `PUT /recurring-rules/:id`: edit rule. Supports query `?scope=all|following&from_date=YYYY-MM-DD`.
- `DELETE /recurring-rules/:id`: delete rule. Supports `?scope=all|following&from_date=YYYY-MM-DD`.
- `GET /tasks?start_date=YYYY-MM-DD&end_date=YYYY-MM-DD`: materializes missing recurring blocks for week, returns all blocks.
- `POST /tasks/:id/move`: keeps existing semantics, supports moving recurring block occurrence (sets `original_date`).

## 4. Recurring Blocks: Materialization & Exceptions

- **Weekly materialization algorithm:**
  When `/tasks?start_date=...&end_date=...` is queried:
  1. Retrieve active rules: `valid_from <= end_date AND (valid_to IS NULL OR valid_to >= start_date)`.
  2. For each rule and matching weekday date in interval:
     - Check existence in `tasks` by `(user_id, recurring_rule_id, date)` OR `original_date = date`.
     - If absent: insert `tasks` row with `source='recurring'`, `status='planned'`.
     - If insert violates time overlap with an active manual block: insert with `status='skipped'` and note `'Conflicted with existing block'`.
     - DB unique index `uq_tasks_recurring_slot` absorbs concurrency races via `ON CONFLICT DO NOTHING`.
- **Exceptions:**
  - **Single occurrence edit:** client sends standard `PUT /tasks/:id` or `POST /tasks/:id/move`. The row updates; `recurring_rule_id` is preserved; if date changed, `original_date` records initial date.
  - **Single occurrence delete/skip:** user taps delete -> sets `status = 'skipped'`. Slot is immediately freed; recurrence engine will not recreate it because row exists.
  - **"This and following" edit:** updates `recurring_rules.valid_to = split_date - 1`; creates new rule with `valid_from = split_date`; deletes unstarted future planned rows (`date >= split_date AND status = 'planned'`) so new rule materializes them.
  - **"This and following" delete:** sets `recurring_rules.valid_to = split_date - 1`; deletes future unstarted planned rows.

## 5. Touch Gestures & View Architecture

- **Scroll vs. Drag on Touch:**
  - Standard touch movement: native scrolling (`touch-action: pan-y`).
  - Drag activation: **long-press (≥ 400 ms)**. A tactile vibration (`navigator.vibrate(20)`) signals pickup.
  - Upon pickup: CSS `touch-action: none` binds to pointer; block elevates with shadow and scale 1.02; top/bottom resize pills appear.
  - Vertical dragging translates block in 15-minute intervals (`step = 15 min = slotHeight / 4`).
  - Releasing pointer drops the block, triggering optimistic UI update and `POST /tasks/:id/move` or `PUT /tasks/:id`.
  - Cancellation: dragging off-screen or tapping outside reverts position without save.
- **Form-Based Alternative:**
  - Double tap or "Edit" button opens `BlockFormModal`.
  - Contains accessible selects for start/end time (15-min increments), category dropdown, date picker, and recurring options.
  - Fully accessible with tab keys, screen reader announcements via `aria-live="polite"`.
- **Mobile vs Desktop Layouts:**
  - Desktop (≥768 px): Full 7-column grid with 00:00–24:00 time gutter. Drag and resize via mouse handles.
  - Mobile (390 px): Sticky top weekday selector (Mon–Sun tabs with load indicators) showing 1 day column at a time with smooth horizontal swipe between days. Auto-scrolls to current time on load.

## 6. Edge cases & principles

- **Timezone & DST:** Recurring rules store wall-clock minutes (e.g. 09:00 = 540 min). When clocks change (DST spring forward/fall back), the block remains at 09:00 wall-clock time in user's zone. Date math calculates `weekdays` using user's IANA timezone.
- **Midnight crossing:** End times can be up to 1440 (24:00). Blocks crossing midnight are rejected in F13 (overnight commitments arrive in F9a).
- **Offline operation:** Recurring rules cached in IndexedDB/localStorage; week materialization runs locally if offline; synced via `sync-queue` on reconnect.
- **Deleted category:** RESTRICT prevents deleting category with existing blocks. User must reassign first.
- **No-shame copy:** Skipped recurring blocks show gentle neutral indicator ("Skipped"), never "Failed" or red alerts. Rest category blocks receive equal visual prominence.

## 7. Security and Privacy

- **Authorization:** Every category and recurring rule endpoint checks `c.MustGet("userID")`. Queries strictly scoped by `user_id = ?`.
- **Data Export & Delete:** `categories` and `recurring_rules` tables added to user data export JSON and cascading account deletion.
- **Logging:** Category names and recurring titles treated as personal data: excluded from Sentry error context and API access logs.
