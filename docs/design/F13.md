# F13 — Planner v2: Categories, Day & Week Views, Recurring Blocks

Spec: M2 items 1, 6, 7. Flag: `FEATURE_F13`. Base: `main` in `discipline`, `discipline-back`, `discipline-py`.
Out of scope: commitments & ICS (M2 #2, #4), weekly targets (M2 #3), Smart Schedule redesign (M2 #9/M6), tasks & Top-3 (M2 #8/F10).

Revision 3 (2026-11-19, approved) — deterministic backfill that keeps every category, nullable
`category_id` with lazy defaults during the deploy, bounded materialization, exceptions instead
of `skipped`, `NO ACTION` foreign keys, no client-side materialization.

## 1. Stories and acceptance criteria

- **S1: Categories (api, web, analytics).**
  - `categories`: `user_id`, `name`, `color`, `icon`, `kind` (`focus`, `study`, `admin`,
    `exercise`, `rest`, `personal`), `system_key`, `name_custom`.
  - AC: six defaults per user (`deep_work`, `study`, `admin`, `exercise`, `rest`, `personal`),
    created **lazily** the first time a user's categories are read or written, so a sign-up
    during the deploy gets them too (§2.4). A default keeps its `system_key`; the web shows the
    translated name (uz/ru/en) until the user renames it, which sets `name_custom = true`.
  - AC: migration 00014 gives **every** existing block a category: one category per distinct
    legacy `tasks.category` string per user, mapped to a kind where we know it, `personal`
    otherwise. No block loses its category, no custom string collapses into Personal (M2).
  - AC: `GET /categories`, `POST /categories`, `PUT /categories/:id`,
    `DELETE /categories/:id[?reassignTo=<id>]`; a category in use without `reassignTo` → 409.
  - AC: names unique per user, case-insensitively: `UNIQUE (user_id, lower(name))`.
  - AC: analytics (`day_metrics`) aggregate by `kind`, never by name.

- **S2: Day and Week planner views (web).**
  - AC: Day view 00:00–24:00, 15-minute grid, auto-scrolls to now.
  - AC: Week view 7 columns (Mon–Sun) from 768 px; on a phone one day column with a weekday pill
    header (no 3-day view — §10.1).
  - AC: drag/resize in 15-minute steps with a mouse; on touch a long press (≥ 400 ms) picks a
    block up while a normal swipe still scrolls.
  - AC: a form dialog does everything the gestures do (keyboard, screen reader), announced with
    `aria-live="polite"`.
  - AC: both views have empty, loading, error and offline states (§5.4).

- **S3: Recurring blocks (api, web).**
  - AC: a rule has weekdays (ISO 1–7, non-empty), start/end minutes, `valid_from`, optional
    `valid_to`, a category.
  - AC: occurrences are materialized server-side, at most 42 days per request, never before
    today, never more than 8 weeks ahead (§4.1).
  - AC: "this one" edits only that occurrence and marks it edited by hand.
  - AC: "this and following" splits the rule and **keeps** individually edited occurrences (§4.4).
  - AC: deleting one occurrence, and a conflict, write a `recurring_exceptions` row — never
    `status = 'skipped'`, which counts against the user (§4.3).

- **S4: Overlap rule with skipped and moved blocks (api).**
  - AC: `checkOverlap` keeps ignoring `status IN ('skipped', 'moved')` (F1 behaviour).
  - AC: materialization never touches an existing block; a clash creates no occurrence and
    records a `conflict` exception.

- **S5: E2E phone planning test (web).**
  - AC: Playwright at 390×844 plans a university timetable, gym 3×/week and 4 focus blocks in one
    scripted pass, with no console error and no horizontal scroll.

### 2.2 Backfill: one category per legacy string, nothing collapsed

```sql
-- One category per (user, mapped name), case-insensitively, so two legacy strings that map to
-- the same name ('gym'/'exercise', 'Reading'/'reading') share one category and
-- uq_categories_user_name cannot be violated. DISTINCT ON makes the survivor deterministic and
-- prefers the mapped row (the one with a system key).
INSERT INTO categories (user_id, name, color, icon, kind, system_key, legacy_name)
SELECT DISTINCT ON (s.user_id, lower(s.name))
       s.user_id, s.name, d.color, d.icon, s.kind, s.system_key, s.legacy
  FROM (SELECT DISTINCT t.user_id,
               lower(btrim(t.category))                      AS legacy,
               coalesce(m.name, left(btrim(t.category), 64))  AS name,
               coalesce(m.kind, 'personal')                   AS kind,
               m.system_key
          FROM tasks t
          LEFT JOIN category_legacy_map m ON m.legacy = lower(btrim(t.category))
         WHERE t.category IS NOT NULL AND btrim(t.category) <> '') s
  JOIN category_defaults d ON d.kind = s.kind
 ORDER BY s.user_id, lower(s.name), (s.system_key IS NULL), s.legacy;

-- Deterministic: exactly one category matches a (user, legacy string) pair.
UPDATE tasks t SET category_id = c.id
  FROM categories c
 WHERE c.user_id = t.user_id
   AND lower(c.name) = lower(coalesce((SELECT m.name FROM category_legacy_map m
                                        WHERE m.legacy = lower(btrim(t.category))),
                                      left(btrim(t.category), 64)));

CREATE INDEX idx_tasks_category_id ON tasks (category_id);
CREATE UNIQUE INDEX uq_tasks_recurring_slot ON tasks (user_id, recurring_rule_id, date)
    WHERE recurring_rule_id IS NOT NULL;
```

Legacy strings in the wild (F1 validation plus the smart schedule): `deep-work`, `study`,
`admin`, `gym`, `rest`, `fixed`, and anything older rows carry. A block with an empty category
string keeps `category_id = NULL` and gets Personal when the API next touches it; 00015 refuses
to run while any `NULL` is left.

### 2.3 The trigger (old writers during the deploy)

The previous API version inserts blocks with the legacy string and no `category_id`. The trigger
fills the id and **never writes `tasks.category`** — overwriting it would rename a custom
category under the old client and spoil a rollback. It resolves in this order, so a category the
user renamed in the new UI is still found instead of being duplicated:

1. `system_key` (from `category_legacy_map`), 2. `legacy_name`, 3. `lower(name)`,
4. otherwise insert one (a user who signed up during the deploy has none yet).

```sql
-- +goose StatementBegin
CREATE FUNCTION tasks_fill_category_id() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE legacy text; m category_legacy_map%ROWTYPE; want_name text; want_kind text;
BEGIN
    IF NEW.category_id IS NOT NULL OR btrim(coalesce(NEW.category, '')) = '' THEN
        RETURN NEW;                                   -- the new API sends the id
    END IF;
    legacy := lower(btrim(NEW.category));
    SELECT * INTO m FROM category_legacy_map WHERE category_legacy_map.legacy = legacy;
    want_name := coalesce(m.name, left(btrim(NEW.category), 64));
    want_kind := coalesce(m.kind, 'personal');
    -- 1. system_key  2. legacy_name  3. lower(name)  4. insert one (ON CONFLICT DO NOTHING,
    -- then read back, so a race or a sign-up during the deploy still gets an id).
    SELECT id INTO NEW.category_id FROM categories
     WHERE user_id = NEW.user_id
       AND (system_key = m.system_key OR legacy_name = legacy OR lower(name) = lower(want_name))
     ORDER BY (system_key IS DISTINCT FROM m.system_key), (legacy_name IS DISTINCT FROM legacy)
     LIMIT 1;
    IF NEW.category_id IS NULL THEN
        INSERT INTO categories (user_id, name, color, icon, kind, system_key, legacy_name)
        SELECT NEW.user_id, want_name, d.color, d.icon, want_kind, m.system_key, legacy
          FROM category_defaults d WHERE d.kind = want_kind
        ON CONFLICT DO NOTHING RETURNING id INTO NEW.category_id;
        IF NEW.category_id IS NULL THEN
            SELECT id INTO NEW.category_id FROM categories
             WHERE user_id = NEW.user_id AND lower(name) = lower(want_name);
        END IF;
    END IF;
    RETURN NEW;
END;
$$;
-- +goose StatementEnd
CREATE TRIGGER trg_tasks_fill_category_id BEFORE INSERT OR UPDATE OF category ON tasks
    FOR EACH ROW EXECUTE FUNCTION tasks_fill_category_id();
```

Down: drop the trigger, function, new indexes and the four `tasks` columns, restore
`chk_tasks_source` to `('manual','smart-schedule')` after
`UPDATE tasks SET source = 'manual' WHERE source = 'recurring'`, then drop
`recurring_exceptions`, `recurring_rules`, `category_legacy_map`, `category_defaults`,
`categories`. `tasks.category` is untouched throughout, so the old code runs again at once.

### 2.4 `EnsureDefaultCategories` (lazy defaults)

Called in one transaction the first time the API reads or writes a user's categories. For each
row of `category_defaults`, in this order — so a user whose legacy string was "Personal" (or any
other default name) does not collide on `(user_id, lower(name))` and does not error on every
call:

1. **Adopt**: `UPDATE categories SET system_key = $key WHERE user_id = $u AND system_key IS NULL
   AND kind = $kind AND lower(name) = lower($name)` — an existing category made by the backfill
   becomes that default, keeping its id, so every block that points at it stays correct.
2. **Insert** what is still missing:
   `INSERT … SELECT … FROM category_defaults … ON CONFLICT (user_id, system_key) DO NOTHING`.
3. **Skip** a default whose name is already taken by a category of a *different* kind: the user
   owns that name, and forcing it would fail the name index. That user simply has five defaults
   plus their own; nothing errors.

## 3. API & contracts

### 3.1 Endpoints (all behind `FEATURE_F13`)

- `GET /categories` → `{ categories }` (ensures the defaults first).
- `POST /categories` `{ name, color, icon, kind }` → 201.
- `PUT /categories/:id` `{ name?, color?, icon? }` → 200; `kind` is immutable, a new name sets
  `nameCustom = true`.
- `DELETE /categories/:id[?reassignTo=<id>]` → 204. With `reassignTo`, blocks and rules move in
  one transaction (same user, different id, else 400 `category_invalid`); without it, a category
  in use → 409 `category_in_use`.
- `GET /recurring-rules` → `{ rules }`.
- `POST /recurring-rules` `{ categoryId, name, weekdays, startMin, endMin, validFrom, validTo? }`
  → 201. Weekdays are ISO, sorted and de-duplicated by the API.
- `PUT|DELETE /recurring-rules/:id?scope=all|following&fromDate=YYYY-MM-DD`.
- `DELETE /tasks/:id/occurrence` → 204: cancels one occurrence (§4.3).
- `POST /recurring-rules/:id/occurrences/:date/place-anyway` → 201: creates the occurrence a
  conflict skipped, overlapping on purpose (§10.2).
- `GET /tasks?startDate=&endDate=` materializes the range (§4.1) and returns
  `{ tasks, exceptions, truncated }`. `GET /tasks?date=` is unchanged.
- `POST /tasks/:id/move` keeps F1 semantics; moving an occurrence sets `original_date`,
  `recurring_edited = true` and writes a `moved` exception for the original date.

Errors: `category_not_found`, `category_in_use`, `category_name_taken`, `category_invalid`,
`category_kind_invalid`, `category_color_invalid`, `category_icon_invalid`,
`recurring_rule_not_found`, `recurring_dates_invalid`, `recurring_weekdays_invalid`,
`range_too_long`, `occurrence_not_found`.

### 3.2 Contracts (`discipline/contracts/`, generated from zod)

- `categories.schema.json`: `Category = { id, name, color, icon, kind, systemKey: string|null,
  nameCustom: boolean }`; `color` is `^#[0-9A-F]{6}$`, `icon`/`kind` enums match §2.1. The web
  renders `nameCustom ? name : t('categories.' + systemKey)`.
- `blocks.schema.json`: `Block` gains `categoryId: number|null`, `categoryKind`,
  `recurringRuleId: number|null`, `originalDate: string|null`, `recurringEdited: boolean`;
  the legacy `category` stays until the column goes.
- `recurring.schema.json`: `RecurringRule`, `RecurringException`
  (`{ ruleId, date, reason }`), range response `{ tasks, exceptions, truncated }`.
- `events.schema.json`: adds `week_planned` (§7). After any zod change:
  `npm run contract:update`, commit `contracts/`.

## 4. Recurring blocks: materialization, exceptions, splits

### 4.1 Materialization (server-side only), with limits

`GET /tasks?startDate=&endDate=`, one transaction per user:

1. A range longer than **42 days** → 400 `range_too_long` (a week view asks 7, a month 42).
2. Clamp: `from = max(startDate, today)`, `to = min(endDate, today + 56 days)`. Dates **before
   today are never materialized** (a block created in the past would count as missed) and nothing
   is created more than **8 weeks** ahead. If the clamp cut something, the response sets
   `truncated: true` and the week view says "planned up to <date>".
3. Rules overlapping `[from, to]`: `valid_from <= to AND (valid_to IS NULL OR valid_to >= from)`.
4. For each rule and matching weekday date (weekday in the user's zone): skip when an exception
   exists for `(rule, date)`, or a row already exists for `(user, rule, date)` or with
   `original_date = date`.
5. Otherwise insert `source='recurring'`, `status='planned'`, the rule's category and minutes,
   `ON CONFLICT DO NOTHING` against `uq_tasks_recurring_slot`, so two devices racing create one.
6. A clash with an existing active block (F1's overlap check, which ignores `skipped`/`moved`)
   creates **no** block and writes a `conflict` exception (§10.2).
7. Past dates are returned from storage as they are: last week shows what happened.

### 4.2 Weekdays and `time.Weekday`

Rules store ISO weekdays (Mon = 1 … Sun = 7). Go's `time.Weekday` is Sunday = 0 … Saturday = 6,
so the API converts with `iso := (int(t.Weekday())+6)%7 + 1` and back with
`time.Weekday(iso % 7)`; both directions are unit-tested across a Sunday, because `Sunday = 0` is
the easy mistake. The SQL uses `extract(isodow from date)`, which is already 1–7.

### 4.3 Exceptions instead of `skipped`

| What the user does | What is stored |
|---|---|
| "Delete just this one" | the occurrence row is deleted when untouched (kept when already done/partial); a `cancelled` exception |
| Materialization hits a clash | no block; a `conflict` exception |
| Moves an occurrence to another day | the row keeps `recurring_rule_id`, gets `original_date` and `recurring_edited = true`; a `moved` exception for the original date |

Exceptions are not blocks: they never appear in `day_metrics`, planned or done minutes, a streak,
or anywhere a miss is counted (`discipline-py` reads `tasks` only, so this holds by
construction). The week view marks the date quietly ("not this week") — never red, never
"failed".

### 4.4 "This one" and "this and following"

- **This one:** `PUT /tasks/:id` or `POST /tasks/:id/move`; the row keeps `recurring_rule_id` and
  gets `recurring_edited = true`.
- **This and following** (`scope=following&fromDate=D`), one transaction:
  1. old rule `valid_to = D - 1`;
  2. new rule `valid_from = D` with the edited values and `split_from_rule_id`;
  3. untouched future occurrences (`date >= D AND status='planned' AND NOT recurring_edited`) are
     deleted, so the new rule materializes them;
  4. occurrences the user edited individually, and any already `done`, `partial`, `in_progress`
     or `moved`, are **kept** and re-pointed at the new rule, so materialization sees them as
     present and does not duplicate them;
  5. exceptions on `date >= D` are re-pointed at the new rule, so a cancelled Wednesday stays
     cancelled across the split.
- **Delete, following:** steps 1 and 3 only; kept rows stay as history.
- **Scope `all`:** the rule and its **future planned** occurrences change; past occurrences keep
  their category and times (§10.6). The past is never rewritten.

## 5. Views, gestures and states (web)

### 5.1 Layout
Desktop (≥ 768 px): 7 columns, 00:00–24:00 gutter, 15-minute grid, mouse drag and resize.
Phone (390 px): one day column, sticky weekday pills (dots for how full a day is), horizontal
swipe between days, auto-scroll to now. Touch targets ≥ 44 px, pills and resize handles included.

### 5.2 Gestures
`touch-action: pan-y` by default so a swipe scrolls. A long press ≥ 400 ms picks a block up
(`navigator.vibrate(20)` where supported, guarded): shadow, `scale(1.02)`, handles,
`touch-action: none` while dragging. Movement snaps to 15 minutes; release saves optimistically
through `POST /tasks/:id/move` or `PUT /tasks/:id`; dragging off-screen or Escape cancels.

### 5.3 Form alternative
"Edit" or double tap opens `BlockFormModal`: date, start/end selects in 15-minute steps,
category, and the recurring options ("only this one" / "this and following"). Labelled inputs,
focus trap, `aria-live="polite"`. Everything a gesture can do is reachable here; the E2E
keyboard pass does the whole flow without a pointer.

### 5.4 Empty, loading, error, offline — both views

| State | Day view | Week view |
|---|---|---|
| Empty | "Nothing planned yet" + "Add a block" (and "Add a repeating block" when the user has no rules) | the same under the pills, for the visible day |
| Loading | skeleton grid with the time gutter already drawn (`aria-busy`), so nothing jumps | skeleton columns; the pill header renders at once |
| Error | the server's translated message + "Try again" (`errorMessage(err, 'planner.loadFailed')`); the grid stays readable | the same, per range request |
| Offline | the **last fetched week from cache**, moves read-only, banner "Offline — showing the week you last loaded"; edits are queued | the same banner above the pills; cached `truncated`/conflict markers are kept |

The client **never materializes** (B7). A rule created or edited offline goes into the existing
`sync-queue` and its occurrences appear once the server answers; the view says "Repeating blocks
appear once you are back online". Block edits queue exactly as in F1, so there is no new offline
machinery.

## 7. Product events

Names live only in `discipline/contracts/events.ts`; the API writes them to `product_events`.
Reused: `block_created`, `block_moved`, `block_status_changed`. New: **`week_planned`**.

| Event | When | Props (no personal data) |
|---|---|---|
| `block_created` | a block is created, materialized occurrences included | `source`, `category_kind` |
| `block_moved` | an occurrence or block moves | `recurring`, `same_day` |
| `block_status_changed` | F1 transitions, unchanged | `from`, `to` |
| `week_planned` | a range is materialized and something was created | `created`, `conflicts`, `days` |

No event carries a category name, rule name or note. Recording follows F1: only on a real
transition, never on a replay.

## 8. Edge cases, security and privacy

- **Timezone & DST:** rules store wall-clock minutes, so 09:00 stays 09:00 after a clock change;
  weekday and "today" come from the user's IANA zone. Tests cover spring-forward and fall-back
  weeks, and an occurrence that lands on the skipped hour (it keeps its minutes).
- **Midnight:** `end_min` up to 1440; blocks crossing midnight are rejected in F13 (F9a).
- **New user:** no rules, no blocks, six lazily created categories; both views show their empty
  state, never an error.
- **Several devices:** materialization is idempotent and guarded by `uq_tasks_recurring_slot`;
  last write wins for a move, as in F1.
- **Deleting a category:** 409 `category_in_use`, or `?reassignTo=<id>` in one transaction.
  `NO ACTION` keeps deleting a **user** working: the cascades remove blocks, rules and categories
  in the same statement.
- **Authorization:** every endpoint takes the user id from the verified token and filters by it;
  `:id` and `reassignTo` are both checked to belong to that user.
- **Export & delete:** `categories`, `recurring_rules`, `recurring_exceptions` join the user data
  export and account deletion.
- **Logging:** category names, rule names and notes are personal data — never logged, never in
  Sentry context, never in an event prop.

## 10. Owner answers (decided 2026-11-19)

1. **No 3-day view for now.** The phone keeps one day column plus the weekday pills.
2. **A conflicting occurrence is not created and never counted.** Materialization writes a
   `conflict` exception; the week view shows a quiet marker with **"place anyway"**
   (`POST /recurring-rules/:id/occurrences/:date/place-anyway`) and **"skip this week"** (turns it
   into `cancelled`). Silently truncating the duration was rejected.
3. **Yes to reassignment on delete:** `DELETE /categories/:id?reassignTo=<id>` in one
   transaction; without it, a category in use still answers 409.
4. **Exceptions live as long as their rule** and are deleted with it (`ON DELETE CASCADE`). No
   cleanup job, no retention window.
5. **Materialization stays in `GET /tasks`** — bounded (§4.1) and idempotent. Revisit when the
   M4 worker can materialize the next two weeks nightly.
6. **A rule edit never rewrites past occurrences.** `scope=all` changes the rule and its future
   planned occurrences only; past ones keep their category and times.

**Decisions taken during the build (owner's authority, "write codes from my authority")**

1. `uq_tasks_recurring_slot` also requires `original_date IS NULL`. F1's move inserts a new row and
   keeps the old one as `moved` on the same `(rule, date)`; without it a same-day move of an
   occurrence violates the index. Materialization treats "row with that date and no
   `original_date`, or a row whose `original_date` is that date" as present (§4.1 step 4).
2. Weekday CHECK: `coalesce(array_ndims(weekdays), 0) = 1`. `array_ndims('{}')` is NULL, so the
   design's CHECK accepted an empty array.
3. Trigger variable renamed `v_legacy`: `legacy` is also a column of `category_legacy_map`, which
   plpgsql rejects as ambiguous.
4. Default categories can be renamed and recoloured but not deleted (400 `category_invalid`):
   lazy creation would bring a deleted default straight back.
5. "Skip this week" needed an endpoint: `POST /recurring-rules/:id/occurrences/:date/skip` (204)
   turns a `conflict` into `cancelled`.
6. The new API writes `tasks.category` = the kind's legacy string (`focus` → `deep-work`,
   `exercise` → `gym`, `personal` → `personal`), so the previous API and analytics keep reading
   known values; the trigger still never rewrites it.
7. `categoryKind` is nullable in `blocks.schema.json` (NULL while a legacy block has no category).
8. Analytics `category_minutes` are summed by kind and keyed by the kind's legacy name, which the
   current web already labels, so `discipline-py` can deploy before the web.
9. `category_defaults.position` orders the defaults (internal table, not in any contract).
10. The range shares `GET /tasks` (`startDate`/`endDate`); `truncated` is set only when the range
    ends after today + 56 days (cutting off the past is not "planned up to").
11. Drags and form edits save with `PUT /tasks/:id` (ids stay stable). On an occurrence a date
    change sets `original_date` and writes a `moved` exception, like `POST /tasks/:id/move`.
12. Offline: gestures are read-only; form edits queue (PUT block, POST block, POST rule) in the F1
    sync queue. React Query assumes "online" at start-up, so the planner queries are disabled
    while `navigator.onLine` is false (no range request offline).
13. `block_created` keeps F1's `category` prop (always one of the five legacy strings, never a name)
    and adds `category_kind`.
