# M1 — Public foundation

**Goal:** a stranger can sign up, recover access, use the app on a phone in their language, and leave with their data.

## Owner prerequisites (decide before the design is approved)
1. **Custom domain.** Web on `app.<domain>`, API on `api.<domain>` (same site). Cookie-based refresh tokens across two `*.up.railway.app` hosts are cross-site and get blocked by browsers that block third-party cookies. Email DNS (SPF/DKIM) and Telegram login (M4) also need a domain.
2. **Transactional email provider** with SPF/DKIM on that domain.
3. **Google OAuth client** (web) for the production and staging domains.

## Must
1. **Auth v2** (closes the rest of F-18)
   - Access token ~15 min, kept in memory only. Refresh token in an `httpOnly; Secure; SameSite=Lax` cookie scoped to the API refresh path; rotated on every use; reuse of an old refresh token revokes the whole family.
   - Refresh endpoint protected against CSRF (Origin check + SameSite).
   - Logout revokes the family; password change revokes all other families (keep `token_version`).
   - Sessions list in Settings: device, last used, revoke.
   - Content-Security-Policy on the web app (no inline scripts; allow only needed origins, incl. Turnstile and Sentry if enabled).
2. **Email verification and password reset**
   - Single-use, hashed, short-lived tokens (verify: 24 h, reset: 30 min).
   - Responses never reveal whether an account exists.
   - Unverified users can use the app; email notifications (M4) require verification.
3. **Google sign-in** (OIDC). Verify issuer, audience, expiry and nonce. Link to an existing account only if both sides have the email verified; otherwise ask the user to sign in and link from Settings.
4. **Onboarding** (≤ 2 minutes, every step skippable, resumable)
   - Language, timezone (auto-detected, confirmed), wake/sleep window, 5-question chronotype quiz (result: morning / intermediate / evening, labeled as self-report), max focus hours per day, preferred rest day.
   - Commitments and goals are added in M2; leave an extension point.
5. **Settings:** profile, language, timezone, sleep window, rest preferences, password, sessions, connected sign-in methods, export, delete account.
6. **i18n:** `uz` (Latin), `ru`, `en`.
   - Every UI string through i18n; dates and numbers via `Intl` in the user's locale.
   - API errors return stable codes; the client translates them.
   - The web check command fails on hardcoded UI strings and on missing keys in any language.
7. **Mobile-first shell:** bottom navigation below 768 px, sidebar above; touch targets ≥ 44 px; PWA manifest + service worker that caches the app shell and shows an offline page; installable.
8. **Legal and trust**
   - Privacy policy and terms pages in 3 languages. Text is a placeholder marked `LEGAL-TODO` until a lawyer reviews it.
   - Consent checkbox at signup; store the accepted policy version and time.
   - Only essential cookies (state this in the policy; no cookie banner needed unless that changes).
9. **Data export and account deletion**
   - Export: JSON + CSV in a zip, all personal data the app stores. Synchronous with a size cap for now (background jobs arrive in M4).
   - Delete: requires re-authentication; hard delete through FK cascades; confirmation email; also removes Redis keys and Sentry user context.
10. **Admin basics** (role-gated): users count, signups per day, active users per day (from `product_events`), feature flags (table + toggles, read by clients at startup), announcement banner.
11. **Product events:** append-only `product_events (user_id, name, props jsonb, occurred_at)`; names defined in `discipline/contracts/`; never send these anywhere else.
12. **Redis outage policy:** rate limiters fail open with an error log and Sentry event; Turnstile is still enforced; `/health` reports `degraded`.

## Should
- react-router 7 and zod 4 upgrades (F-26 leftovers).
- Dark mode via design tokens.

## Acceptance criteria
- New user on a 390 px phone: signup → verify email → onboarding → empty Today screen in under 3 minutes, in each of the 3 languages.
- Password reset works end to end; an unknown email gets the same response and timing class as a known one.
- Stolen refresh token: using it after the real client refreshed revokes the family (test).
- Export contains every table row that belongs to the user (test enumerates tables with `user_id`); delete leaves zero rows.
- No hardcoded UI strings (web check command green).
- Lighthouse PWA installable; offline page shown with network off.

## Events
`signup_completed`, `email_verified`, `onboarding_step_completed`, `onboarding_completed`, `login`, `password_reset_completed`, `export_requested`, `account_deleted`.

## Out of scope
Telegram login (M4), notifications (M4), commitments and goals (M2).
